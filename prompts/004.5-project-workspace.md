# Phase 004.5: Project Workspace

## Status

IMPLEMENTED (2026-09-05) — the founder's kickoff message explicitly authorized proceeding directly to the smallest complete implementation since the design fit cleanly on existing infrastructure (no new permission family, no new RLS primitive, no new dependency). Built and verified: `npm run typecheck`/`lint`/`test` (147/147)/`build` all clean, browser bundle secret scan clean, live RLS impersonation confirmed Contractor same-company section/block isolation, forged-project-id section-creation denial, cross-project block-movement rejection via the new `enforce_block_section_project_match` trigger, Viewer mutation denial (with read access confirmed still working), and founder org-level visibility across both test projects.

**Hardening found and fixed during implementation:** the security advisor flagged both new trigger functions (`enforce_block_section_project_match`, and Phase 004's pre-existing `enforce_decision_project_scope`) as RPC-executable by `anon`/`authenticated`. The first fix attempt (revoking from `anon, authenticated` directly, matching migration `0009`'s pattern) did not actually work — confirmed via `has_function_privilege()` that both roles could still execute the functions afterward, because they inherit an implicit grant through the `PUBLIC` pseudo-role that a direct-role revoke doesn't remove. Migration `0025` fixes this correctly by revoking from `PUBLIC` itself. Re-verified live that both triggers still fire normally afterward (a database trigger runs independent of the invoking role's own EXECUTE privilege on the function). **Note for a future pass:** this same gap (revoke-from-role instead of revoke-from-PUBLIC) affects Phase 001's original `handle_new_user`/`has_company_permission`/`has_org_permission`/`is_company_member` hardening in migration `0009` — confirmed still present by the same advisor scan. Left untouched here as out of scope for this phase, but flagged for the founder's attention.

## 1. Objective

Make each project's Overview page a flexible, section-and-block workspace — Notion-like in feel — layered strictly on top of Phase 004's structured operational tables, never replacing them. A project's real tasks, deliverables, milestones, scope changes, decisions, and audit trail remain exactly what they were; the workspace adds a customizable presentation and note-taking layer around them so Orextic and Orex Studios projects can look different (Creative Direction + Shot List vs. Discovery Notes + Automation Map) without any schema fork.

## 2. Existing Phase 004 Foundation (reused as-is)

`has_project_access(projectId, permissionKey)` (migration `0019`) — reused unmodified as the sole authorization primitive for every new table. `projects.read`/`projects.update` (existing keys) — reused verbatim, no new permission family. `lib/projects/activity.ts` (`writeProjectActivity`) and `lib/audit` (`writeAuditLog`) — reused unmodified for structural workspace events. `lib/projects/url-safety.ts` (`assertSafeReferenceUrl`) — reused for the `link` block type and any URL a `project_view`/table cell might contain. The existing `[projectId]/layout.tsx` tab nav (Milestones/Tasks/Deliverables/Readiness/Scope/Activity/Team/Decisions) is unchanged and remains the authoritative, always-reachable route for each system module — the workspace's system-section cards are a summary/shortcut layer on top, never a replacement.

## 3. Scope

Two new tables (`project_sections`, `project_blocks`); a reworked Overview page rendering them section-by-section; 8 block types (`text`, `heading`, `callout`, `checklist`, `table`, `divider`, `link`, `project_view`); a lightweight JSONB-validated custom table; a `project_view` block that queries real Phase 004 tables at render time (never copies rows); section/block CRUD and up/down reordering; structural audit/activity events (not per-keystroke). Default workspace seeded on project creation (3 custom sections + 8 system-section presentation rows) and lazily backfilled for the pre-existing projects created during Phase 004's manual testing.

## 4. Out of Scope

Clients, Calendar (per explicit instruction). Any redesign of the global Orex OS shell or the existing tab routes. A generic, application-wide block system (this is Project Workspace V1, scoped to projects only). Relations/rollups/formulas/automations/linked databases in the custom table. A full project-template management system (the schema is shaped so one can be added later without migration, but none is built now). AI over workspace content (explicitly deferred to the intelligence phase). Real drag-and-drop (see §9 — up/down controls instead, since no drag-and-drop dependency exists in the stack today and adding one for this alone would be disproportionate to "smallest complete implementation").

## 5. Data Model

### `project_sections`
```
id                uuid pk
organisation_id   uuid not null references organisations(id)
company_id        uuid references companies(id)
project_id        uuid not null references projects(id) on delete cascade
title             text not null
section_type      text not null check (section_type in ('system', 'custom'))
system_key        text check (system_key in (
                    'milestones','tasks','deliverables','readiness',
                    'scope','team','decisions','activity'))
                  -- required (not null) when section_type = 'system', must
                  -- be null when section_type = 'custom' (CHECK constraint)
position          integer not null default 0
is_collapsed      boolean not null default false
is_hidden         boolean not null default false
created_by        uuid references user_profiles(id)
created_at        timestamptz not null default now()
updated_at        timestamptz not null default now()
```
`organisation_id`/`company_id` are denormalized from the parent project (same reasoning as `project_readiness_checks` in Phase 004: avoids an extra join in every RLS policy, independently inspectable). A system section's `system_key` never changes after creation and is never user-editable — it identifies which Phase 004 module the card summarizes; the row itself only carries *presentation* state (position/collapsed/hidden), never a copy of the module's data.

### `project_blocks`
```
id                uuid pk
organisation_id   uuid not null references organisations(id)
company_id        uuid references companies(id)
project_id        uuid not null references projects(id) on delete cascade
section_id        uuid not null references project_sections(id) on delete cascade
block_type        text not null check (block_type in (
                    'text','heading','callout','checklist','table','divider','link','project_view'))
position          integer not null default 0
content           jsonb not null default '{}'::jsonb
created_by        uuid references user_profiles(id)
updated_by        uuid references user_profiles(id)
created_at        timestamptz not null default now()
updated_at        timestamptz not null default now()
```
`project_id` is kept explicit (not derived solely via `section_id`) for the reason the founder's brief flagged: it materially improves RLS safety by letting `project_blocks`' own policy check `has_project_access(project_id, ...)` directly, and — combined with a database trigger (§7) — makes "a block's `project_id` must equal its section's `project_id`" a real constraint, not just an assumption. Blocks only ever belong to `custom` sections in this version (system sections render their summary directly from Phase 004 tables, never from blocks) — enforced in the server action, not the schema, since a future version may legitimately want blocks under a system section.

## 6. Block Content Schemas (Zod, `lib/validation/project-blocks.ts`)

```
text:         { text: string }
heading:      { text: string, level: 1 | 2 | 3 }
callout:      { text: string, tone: 'info' | 'warning' | 'success' | 'danger' }
checklist:    { items: [{ id: string, text: string, checked: boolean }] }
divider:      {}  -- no content
link:         { url: string, label: string }  -- url validated via assertSafeReferenceUrl
table:        { columns: [{ id, name, type: 'text'|'number'|'select'|'checkbox'|'date'|'url', options?: string[] }],
                rows: [{ [columnId]: string | number | boolean | null }] }
                -- max 20 columns, max 500 rows -- prevents an unbounded blob
project_view: { sourceType: 'tasks'|'milestones'|'deliverables'|'scope_changes'|'readiness_checks',
                displayMode: 'list' | 'count',
                filter?: { status?, approvalState?, isBlocking? }  -- whitelisted per sourceType
                sort?: { field: <whitelisted per sourceType>, direction: 'asc'|'desc' } }
```
Every block's `content` is validated server-side against the schema matching its `block_type` before insert/update — never trusted as opaque JSON. `project_view`'s `filter`/`sort` fields are validated against a small per-source-type whitelist (e.g., `tasks` only accepts `filter.status` and `sort.field` in `{due_date, created_at, priority}`) so it can never be used to reference an arbitrary column or bypass RLS — it configures a fixed, known query shape per source type, never a free-form query.

## 7. Cross-Project Integrity (database trigger)

Mirrors the `enforce_decision_project_scope` pattern added during Phase 004's closure hardening:
```sql
create or replace function public.enforce_block_section_project_match()
returns trigger language plpgsql security definer set search_path = public as $$
declare sec record;
begin
  select project_id, organisation_id, company_id into sec from project_sections where id = new.section_id;
  if not found then raise exception 'project_blocks.section_id references a non-existent section'; end if;
  if sec.project_id is distinct from new.project_id then
    raise exception 'project_blocks.project_id must match its section''s project_id';
  end if;
  return new;
end; $$;
```
This is what makes "cross-project block movement rejection" a real, always-enforced invariant rather than a hope resting on application code alone — a block's `section_id` can never be repointed at a section belonging to a different project, at the database level, regardless of which code path attempts it.

## 8. Default Workspace

On `createProject()` (Phase 004's existing action, extended): seed 3 custom sections (`Project Summary`, `Current Work`, `Delivery`, all empty) and 8 system-section presentation rows (one per `system_key`, in a fixed sensible order, all visible/expanded by default). For the projects already created during Phase 004's manual testing (which predate this table), a small idempotent helper (`lib/projects/workspace.ts`'s `ensureDefaultWorkspaceSections(projectId, ...)`) is called once at the top of the Overview page's render — if a project has zero `project_sections` rows, it creates the same default set before the page queries them. No project is ever forced to keep this layout — every section can be renamed, reordered, hidden, or (for custom sections) deleted immediately after.

## 9. Editor UX

Reordering uses simple up/down buttons per section/block, not drag-and-drop — the codebase has zero drag-and-drop dependency today (verified by inspection), and adding one (e.g. `@dnd-kit`) solely for this feature would be a disproportionate new-dependency decision against "prefer purpose-built Orex blocks... do not introduce a huge editor framework unless necessary." Up/down achieves the same reordering outcome with zero new dependencies; a future pass can upgrade to real drag-and-drop if the up/down interaction proves too slow in practice. Each block type has its own small inline-editable component (edit-in-place, save on blur/explicit confirm for structured types like the table) rather than a shared rich-text framework. System sections render as a compact summary card (a count/status line plus a link to the existing full tab route) — never a duplicate of the tab's table.

## 10. Permissions

No new permission keys. `projects.read` (via `has_project_access`) gates viewing sections/blocks; `projects.update` gates every mutation (create/rename/reorder/hide/collapse/duplicate/delete section; create/edit/delete/reorder block). This matches the founder's own recommendation and the instruction not to create a new permission family without genuine need — workspace content is exactly as sensitive as the rest of a project's operational surface a `projects.update` holder already manages, not a distinct trust tier. Contractor resource-scoping applies automatically since `has_project_access` is the same function used everywhere else in Phase 004.

## 11. RLS

```sql
-- project_sections
select:  has_project_access(project_id, 'projects.read')
insert:  has_project_access(project_id, 'projects.update')
update:  has_project_access(project_id, 'projects.update')
delete:  has_project_access(project_id, 'projects.update')

-- project_blocks (own project_id column, no join needed)
select:  has_project_access(project_id, 'projects.read')
insert:  has_project_access(project_id, 'projects.update')
update:  has_project_access(project_id, 'projects.update')
delete:  has_project_access(project_id, 'projects.update')
```
Combined with the trigger in §7, a forged `project_id` on section/block creation is denied by RLS before the trigger is even reached; a legitimate `project_id` with a `section_id` from a different project is denied by the trigger even if RLS alone would have allowed the write (defense in depth, same as Phase 004's other indirect tables).

## 12. Project Data Views

`project_view` blocks never copy rows into `project_blocks.content` — only configuration. Rendering happens in the Overview page's server component: a fixed `switch` on `sourceType` runs the corresponding real query (`project_tasks`, `project_milestones`, `project_deliverables`, `project_scope_changes`, `project_readiness_checks`) through the normal RLS-enforced server client, applying only the whitelisted filter/sort from the block's validated config. Because the query goes through the same client and tables as the dedicated tab pages, it is exactly as permission-safe as those pages — there is no separate, weaker path.

## 13. Audit / Activity

Structural events only, via the existing `writeAuditLog`/`writeProjectActivity`: `project_section.created`, `project_section.renamed`, `project_section.deleted`, `project_block.created`, `project_block.deleted`, `project_layout.changed` (one event per reorder/hide/collapse action, not per drag step). Block *content* edits (text, checklist items, table cells) update `updated_at`/`updated_by` only — no audit or activity row per edit, per the founder's explicit "not one row per keystroke" instruction.

## 14. Security

No block type stores credentials — `link`/`table`(url column)/`project_view` reference-URL-shaped fields all pass through `assertSafeReferenceUrl`. No AI integration in this phase — workspace content is never sent to `lib/ai/*`. Custom section/block content follows normal company-scoped RLS; no new classification tier is introduced (content inherits the project's own sensitivity discipline, same as everything else in Phase 004).

## 17. Acceptance Criteria

1. A Contractor assigned to Project A cannot read or mutate Project B's sections/blocks — live-verified, not assumed.
2. A forged `project_id` cannot create a section; a `section_id` belonging to another project cannot be used to create or move a block into it — both denied before any row is written.
3. Hiding a system section never deletes or restricts access to its underlying data — the dedicated tab route remains fully reachable regardless of workspace hide state.
4. A `project_view` block never returns a row the viewer's normal RLS-enforced access wouldn't already return.
5. No audit or activity row is written for a routine block-content edit; structural events (create/rename/delete/reorder) are audited.
6. Viewer role can see the workspace but cannot create, edit, reorder, or delete anything in it.
